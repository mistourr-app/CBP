## 1. Зачем этот этап

Прототип написан за 5 минут и работает, но под ним нет базы для развития. `SYSTEMS_SPEC.md`
описывает принципиально другую игру (тиры ресурсов, налоговый маятник, счастье −2..+2,
социальные здания, события с выборами) — она не реализована вообще.

Цель этапа 1 — **не менять геймплей**, а построить фундамент, на котором спеку можно
реализовывать по частям:

1. все числа в одном файле `js/balance.js`;
2. игровое ядро не зависит от браузера — его можно тестировать и прогонять симуляциями;
3. PWA реально работает офлайн и устанавливается;
4. 3D без визуальных багов;
5. единая дизайн-система вместо правок «поверх».

## 2. Решения по итогам обсуждения

| Вопрос | Решение |
|---|---|
| Что считать ТЗ | Сначала фундамент, `SYSTEMS_SPEC.md` реализуется на этапе 2 |
| Стек | ES-модули без сборки, тесты — встроенный раннер Node (`node --test`). Ноль зависимостей |
| Графика | 3D сохраняется, но переделывается под капотом; Three.js вшивается локально |
| Камера | Угол фиксированный; при росте города плавно отъезжает, чтобы город влезал в экран |
| Дизайн | Чинить визуальные баги, не изобретать новый стиль |
| Геймплей | Чинить явные баги, числа и поведение не менять |
| Сохранения | Старые сейвы сбрасываются (их формат изменится) |
| Иконки | Только SVG, без генерации PNG |
| Коммиты | По одному на этап, чтобы любой этап можно было откатить |

### Главное архитектурное правило

`js/game/**` и `js/balance.js` **не знают про DOM и про Three.js**. Именно это позволяет
запускать игровую логику в Node и тестировать её без браузера.

Слои зависят только сверху вниз:

```
ui  →  render  →  game  →  core  →  balance
```

## 4. Этапы работ

### Этап 0. Инфраструктура

- `package.json`: `{"type": "module"}`, скрипты `npm test` и `npm start`. Зависимостей нет.
- `serve.js`: статический сервер на встроенном `http`, правильные MIME (`.js`, `.svg`,
  `.webmanifest`), корректная работа при запуске из подпапки (`/CBP/`).
- `.gitignore`.
- Скачать `three@0.169.0/build/three.module.min.js` в `vendor/`.
  - Почему 0.169.0, а не актуальный 0.186.1: начиная с ~0.167 сборка разделена на
    `three.module.js` + `three.core.js`, и минифицированный модуль импортирует
    невыминифицированное ядро. Для оффлайна нужен один самодостаточный файл.

### Этап 1. Баланс и ядро игры

- **`js/balance.js`** — единственный источник чисел. Сейчас они продублированы в трёх
  местах и разъезжаются: `js/gameState.js:497+` (реальные списания), `js/system.js:19+`
  (условия показа), `js/main.js:536+` (блокировка кнопок).
- **`js/core/rng.js`** — `mulberry32` с сидом, сид хранится в сейве. Нужен для симуляций,
  которые просит `SYSTEMS_SPEC.md` §7.
- **`js/core/save.js`** — сейв с `schemaVersion`; несовпадение версии → сброс. Ключ
  `cbp.save.v2`.
- **`js/core/bus.js`** — шина событий, чтобы UI не знал про рендер и наоборот.
- **`js/game/economy.js`** — **один** расчёт дня. Сейчас производство считается дважды
  (`js/gameState.js:213` и `js/gameState.js:307`); правка одной копии не трогает вторую.
  Заменяется единым `computeDaily(state)`, который используют и тик дня, и превью в UI.
- **`js/game/engine.js`** — дневной цикл: сезон → рабочие → потребление → производство →
  событие → условия окончания. Разделение победы и поражения.
- **`js/game/state.js`** — чистая модель без побочных эффектов.

**Чинимые игровые баги (поведение и числа не меняются):**

| Что | Где сейчас |
|---|---|
| В хронику пишется «День N» каждый день, буфер всего 20 строк → важные события вытесняются | `js/gameState.js:265` |
| Кнопки найма/увольнения — пустышки: `autoAssignWorkers()` всё равно заполняет слоты сам | `js/gameState.js:164` против `js/system.js:57-109` |

| Двойные обработчики клика на кнопки выбора; спасает только флаг + секундная блокировка ввода | `js/main.js:584` + `js/main.js:725` + `js/main.js:613` |
| Один экран и для победы, и для поражения, надпись «ИГРА ОКОНЧЕНА» даже при победе | `js/main.js:652` |

Решение по найму: автоназначение остаётся (это текущее поведение), а мёртвые кнопки найма
и увольнения убираются из пула выборов — занятость показывается в интерфейсе.

### Этап 2. Контент

- **`js/game/choices.js`** — генерация 4 слотов на данных из `balance.js` вместо
  200-строчной цепочки `if`. Гарантии: всегда 4 варианта, всегда есть «Подождать»,
  никогда нет недоступного варианта, нет дублей.
- **`js/game/content.js`** — тексты, иконки, названия зданий и события выносятся из кода
  в данные, чтобы на этапе 2 их можно было дописывать данными, а не кодом.
- **`js/game/chronicle.js`** — записи `{day, icon, kind, text}`, без шума, без дублей,
  300 записей в состоянии, 60 в DOM, точечное добавление узлов.

## 5. Чего НЕ делаем на этом этапе

Реализация `SYSTEMS_SPEC.md`:

- тиры ресурсов и смена тира, выбывание старых ресурсов;
- налоговый маятник (ставка 10–50%), `tierTaxMult`;
- счастье как уровень −2..+2 вместо шкалы 0–100;
- социальные здания как якоря счастья;
- события с выборами и временными эффектами;
- финальный проект и престиж.

Архитектура этапа 1 готовит под это: в `balance.js` будут заложены секции под эти системы,
а `content.js` позволит добавлять их данными, а не кодом.

## 8. Этап 2 — SYSTEMS_SPEC.md

Целевая игра описана в `SYSTEMS_SPEC.md`. Это не доработка, а замена
экономики: доход идёт от налогов, счастье становится дискретным, ресурсы
меняются по тирам, события получают выборы.

Работа разбита на подэтапы. Каждый завершается рабочей версией игры.

### 2.1. Счастье и налоги

Ядро новой экономики — **налоговый маятник**: игрок поднимает налог,
доход растёт, но народ недоволен, жители уходят и доход падает. Налог —
постоянная политика, а не действие каждого хода.

| Что | Было | Станет |
|---|---|---|
| Счастье | число 0–100, падает на 1 в день | уровень −2..+2, считается каждый день |
| Доход | рынки производят золото рабочими | жители платят налог: 1–5 золота с жителя в день |
| Рынки | производят золото | социальное здание: надбавка к сбору налога |
| Уход жителей | только от голода | от недовольства: 5 в день при −2, 2 при −1 |

Ставка налога меняется действием в выборах и не занимает слот каждый
ход — иначе игрок не смог бы ею пользоваться.

Сделано в подэтапе 2.1:

- уровень счастья `−2..+2` пересчитывается каждый день с нуля: база от
  ставки налога плюс «Религия» с храмом (`+1`) и события; ничего не копится;
- отток при `−2` — 5 жителей в день, при `−1` — 2, выше нуля — рост
  производства `×1.1` и `×1.25`;
- золото больше не производится рабочими: казна получает налог с жителей,
  рынки добавляют к сбору с каждого жителя;
- смена ставки — действие хода, предлагается раз в 3 дня и перебирает ставки
  по кругу;
- в интерфейсе показатели «Счастье» и «Налоги» покаются уровнем и ставкой
  словами, а не процентами, и стоят в одной строке с населением;
- состояние и хранилище подняты до схемы 3: счастье ушло из ресурсов,
  старые сохранения отбрасываются.

### Уровни поселения и постройки (схема 4)

Постройки и ресурсы описаны в `js/balance.js`, раздел `buildings`,
`resources`, `development`. Правила:

- здание не требует другого здания; требование одно — свободные жители
  для производственных;
- производственное здание даёт один ресурс и работает только на своём
  уровне; на других уровнях не учитывается и не требует обслуживания;
- социальное здание даёт эффект, который действует на всех уровнях, если
  построено; строится только на своём уровне;
- эффекты одного типа суммируются;
- дороги накапливаются без лимита, стоимость растёт с уровнем;
- религия, храм, часовня и вера удалены;
- пищевой ресурс меняется по уровням: зерно → мука → мясо → деликатесы.

Отклонения, которые нужно подтвердить по симуляции:

- стоимость построек уровней 2–4 только золотом: требования перехода
  списывают материалы, и без золота к следующему уровню не построить
  производство (тупик). Материалы для стоимости нужны только на уровне 1;
- длительности пожара, эпидемии, засухи и бури пока не работают: события
  с временными эффектами — подэтап 2.3. Эффекты огня и больниц записаны
  числами (`fireDays`, `epidemicLossReduction`) и подключатся туда;
- победа — достижение последнего уровня; итоговый проект — подэтап 2.5;
- ресурсы прошлых уровней скрыты, но запасы в них остаются в партии.

### Сделано вне очереди

Два правила из ТЗ оказались неотложными, их внесли сразу, не дожидаясь
своих подэтапов:

- **прирост населения убран.** Пассивного «+1 житель в день» больше нет:
  новые люди приходят только через постройку домов и события с выбором
  (`SYSTEMS_SPEC.md` §2). Город, который растёт сам, отнимает у игрока
  решение о застройке;
- **прогресс к следующему уровню в панели ресурсов.** Требования уровней
  описаны в `BALANCE.development` (`SYSTEMS_SPEC.md` §6), и карточки
  ресурсов показывают «собрано из целевого» с полосой: сейчас это дерево,
  камень и еда по 100 единиц для перехода Поселение → Деревня. Сам переход
  на уровень появится в 2.4 вместе с новыми ресурсами.

### Что не меняется

Баланс ресурсов и зданий остаётся прежним, чтобы подэтапы не накладывались
друг на друга. Переход на тиры ресурсов — 2.4.

Открытые вопросы спеки, которые надо решить при плейтесте:

- стакаются ли эффекты нескольких копий одного социального здания;
- что наследует следующее поселение после победы.
